# Scaling & capacity (#113)

How the Reload server scales horizontally, the knobs that bound one box's capacity, and how to size the
fleet from **measured** numbers. The capacity numbers themselves live in
[`capacity.md`](capacity.md) — regenerated by the load suite, never hand-typed. See
[ADR-0113](adrs/0113-performance-capacity-rails.md).

## The server is stateless

Every request can be served by any replica: there is **no in-memory session affinity**. Session and
auth state lives in **Postgres** (the `sessions` table, hashed token → user) and the cross-cutting
runtime flags live in **Redis** (the #99 maintenance flag, presence). The admission counters (#71) are
per-process but are *capacity accounting*, not request state — a request never needs "its" instance.

This is proven, not asserted: `test/integration/perf-statelessness.test.ts` mints a session on one app
instance and authenticates it on a **second, separate** instance over the same Postgres/Redis. Because
that passes, you can run N replicas behind a round-robin load balancer with no sticky sessions.

**Scale-out recipe:** run more server processes/replicas (each is identical), point them at the same
`DATABASE_URL` + `REDIS_URL`, and load-balance round-robin. No leader, no shared memory, no sticky
sessions. Throughput is linear in replicas until a shared backend (Postgres, Redis) becomes the
bottleneck — watch the saturation alerts below for that.

## Worker-concurrency knobs (the capacity ceiling per replica)

| Knob | Env / config | Default | What it bounds |
| --- | --- | --- | --- |
| **PG pool size** | `DATABASE_POOL_MAX` (env) | `10` | DB-bound concurrency per process. The dominant per-replica ceiling — raise it (and Postgres `max_connections`) before adding replicas if `pg_pool_connections{state="waiting"}` is non-zero. |
| **Per-tenant in-flight sessions** | `scale.tenantConcurrency` (config) | `0` = unlimited | One tenant's runaway loop can't starve the fleet. |
| **Fleet-wide in-flight sessions** | `scale.globalConcurrency` (config) | `0` = env default | The whole box's session ceiling (the admission chokepoint, #71). |
| **Team-run parallelism** | `TEAM_MAX_CONCURRENCY` (env) | `3` | Parallel agents within one team run. |
| **Warm-pool buffer** | `scale.warmPoolSize` (config) | `0` = off | Pre-provisioned sandboxes for fast launch (#71). |
| **Per-session caps** | `AGENT_WALLCLOCK_MS` / `AGENT_IDLE_MS` / `AGENT_MEMORY_MB` (env) | 600s / 120s / – | A single session's blast radius. |

The pg pool size is the one most people get wrong: a pool of 10 means at most 10 concurrent DB-bound
requests *per replica*, regardless of how many cores the box has. The capacity suite's `agent-api-read`
scenario (auth + DB read) is the one that exercises it.

## Saturation signals (when to add capacity)

`GET /metrics` exports the four signals that predict a melting box (sampled at scrape time, fail-soft).
Thresholds live in `src/observability/saturation.ts` and fire the alerts in `observability/alerts.yml`
(wired to the #112 SRE alerts; the same `classifySaturation` verdict is the seam the #105 watchdog can
consult):

| Metric | Meaning | Add capacity when |
| --- | --- | --- |
| `event_loop_lag_seconds` | Mean Node event-loop delay | sustained > 50ms (warn) / 200ms (critical) → CPU-bound; add replicas |
| `pg_pool_connections{state="waiting"}` | Requests blocked on a DB connection | > 0 sustained → raise `DATABASE_POOL_MAX` or scale Postgres |
| `redis_ping_seconds` | Redis round-trip latency | > 250ms → Redis is the bottleneck |
| `queue_depth` | Fleet sessions in flight (admission) | approaching `globalConcurrency` → near the session ceiling |

## Sizing the fleet from measured numbers

The capacity model in [`capacity.md`](capacity.md) reports **req/s per vCPU** for each hot path,
measured by `pnpm -C platform --filter @reload/server perf` (the closed-loop driver, not a guess). To
size the fleet:

1. Take the `baseline` **req/s per vCPU** (the framework anchor) from `capacity.md`.
2. Divide your expected **peak req/s** by it to get the vCPU count, then by your replica size to get
   replica count.
3. Add headroom so you sit below the saturation warn thresholds at peak (rule of thumb: target ≤ 70%
   of the measured single-replica throughput).
4. Confirm the shared backends scale too: Postgres `max_connections ≥ replicas × DATABASE_POOL_MAX`.

## Cost forecast + infra budget ceiling

Per-workspace compute cost is forecast from the `tenant_usage` trend (`src/scale/forecast.ts`) and
surfaced in the Founder Console (#104): next month's projected spend, a right-sizing recommendation
(scale up/down/hold from live utilization), and — when `scale.infraBudgetCeilingCents` is set — a
**projected breach** warning so hosting can never surprise-bill (links #108). The ceiling is a
read-only *warning*; the #71 per-window `budgetCents` cap remains the only thing that actually blocks a
launch.
