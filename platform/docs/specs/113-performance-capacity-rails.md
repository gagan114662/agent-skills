> (Founder Console roll-up), **#105** (fleet watchdog), **#108** (ipop hosting / infra budget link).
> Lifecycle: **DEFINE** artifact (`spec-driven-development`) → atomic plan → TDD failing-first → ADR →
> one PR. **Video gate waived by the owner.**

## Objective

**What:** Replace capacity-by-vibes with capacity-by-measurement. Today nobody has measured what one
box can handle, so an HN hug or a runaway loop could saturate every venture at once and our scaling
and optimization decisions are guesses. This slice adds four rails:

1. **A load-test suite + CI perf budgets.** A dependency-free, closed-loop load driver hammers the hot
   paths (the agent/session API surface, the #98 billing webhook verify path, a framework baseline)
   and produces a `PerfResult` per scenario (req/s, p50/p99 latency, error rate). A pure
   `evaluateBudgets` gate compares each result against a declared `PerfBudget`; a regression past the
   budget exits non-zero. The suite runs **locally** (`pnpm --filter @reload/server perf`) and as a
   dedicated **CI `perf` job** that fails the PR on a budget breach.
2. **Saturation metrics at `/metrics`.** The four signals that predict a melting box — **queue depth**
   (admission in-flight), **event-loop lag**, **PG pool wait** (waiting/total/idle), and **Redis ping
   latency** — are sampled at scrape time and exported in the #19 registry. A pure
   `classifySaturation` maps a sample to `ok | warn | critical` against thresholds; new Prometheus
   rules in `alerts.yml` turn those into the #112 SRE alerts and the same classifier is the seam the
   #105 watchdog can consume.
3. **A scaling policy backed by measurement.** Prove the server is **stateless** (no in-memory session
   affinity — session/auth state lives in Postgres/Redis) with an integration test that signs up on
   one app instance and authenticates on a second instance over the same stores. Expose the **worker
   concurrency knobs** that govern capacity (`DATABASE_POOL_MAX`, the existing `scale.tenantConcurrency`
   / `scale.globalConcurrency` / `TEAM_MAX_CONCURRENCY`) and document horizontal scale-out with a
   **measured req/s-per-vCPU** capacity model produced by the suite (`docs/capacity.md`, regenerated by
   the run — never hand-typed).
4. **A cost forecast + infra budget ceiling.** A pure `forecastUsage` projects next window's
   compute-seconds and cost from the `tenant_usage` trend; `recommendRightSizing` turns utilization +
   the projection into a scale-up/down/hold recommendation; `infraBudgetStatus` flags when the
   projection would breach a configured **infra budget ceiling** (`scale.infraBudgetCeilingCents`,
   linking #108 so hosting can never surprise-bill). All three surface in the Founder Console (#104).

**Why:** "Premortem (owner directive): nobody has measured what one box can handle. An HN hug or a
runaway loop kills every venture at once; capacity and optimization decisions are vibes, not
measurements." Rails, not heroics: a budget that fails the PR, a metric that fires an alert, a number
in the docs, a forecast that warns before the bill.

**Who:** Operators sizing the fleet (the capacity model + saturation alerts); a founder (Gagan) who
needs the infra bill bounded and right-sizing surfaced in the daily review; every venture, which must
not be taken down by a neighbor's runaway loop.

## The pure cores (the testable gates)

Like #17 `decideWorkflowAction`, #96 `decideVenture`, and #105 `decideRevival`, the judgment lives in
pure, fully unit-tested functions; the IO orchestrators only gather inputs and apply effects:

- `evaluateBudgets(results, budgets) → { ok, violations[] }` and `summarize(samplesMs) → { p50, p99, … }`
  (`perf/budgets.ts`) — the regression gate + percentile math.
- `classifySaturation(sample, thresholds) → { level, reasons[] }` (`observability/saturation.ts`) — the
  saturation verdict that feeds alerts + the watchdog.
- `forecastUsage(trend, nextWindow)`, `recommendRightSizing(input)`, `infraBudgetStatus(projected, ceiling)`
  (`scale/forecast.ts`) — the cost projection, right-sizing call, and ceiling gate.

## Default OFF / additive (unchanged behavior)

- **No migration.** The forecast reads existing `tenant_usage` rows; the config additions extend the
  already-threaded `scaleSchema` (no new top-level config block, so no `layers.ts` allowlist change);
  saturation is runtime-only. By-issue numbering (the `0113` slot) is reserved should a migration ever
  be needed — none is.
- **Saturation metrics are always-on but free:** scrape-time sampling reads pool counters (in-memory),
  one event-loop-delay histogram mean, and one bounded Redis `PING` (timed out, fail-soft to "absent")
  — no new persistent state, no tenant labels (the #19 cardinality rule).
- **The infra budget ceiling defaults to `0` = no ceiling**, mirroring `scale.budgetCents`; right-sizing
  and the forecast are read-only — they never block a launch (that stays the #71 admission/budget job).
- **`DATABASE_POOL_MAX` defaults to `10`** (today's hard-coded value) — purely a knob, no behavior change
  unless set.

## Acceptance criteria (from #113 — BUILD/TDD)

1. **CI perf job enforcing budgets** — a dedicated `perf` job (PG+Redis services) runs the suite and
   fails the PR when any scenario regresses past its `PerfBudget` (min req/s floor, max p99, max error
   rate). The gate (`evaluateBudgets`) is pure and unit-tested for pass, each violation kind, and the
   no-budget case.
2. **Load driver is correct + deterministic** — `runLoad` drives exactly `totalRequests` at the
   configured `concurrency`, counts errors, and returns percentile/throughput stats; unit-tested with an
   injected clock + fake request fn (no network) so the math is deterministic.
3. **Saturation metrics integration-tested** — `GET /metrics` on a booted app exposes
   `event_loop_lag_seconds`, `pg_pool_connections{state=…}`, `queue_depth`, and (when Redis is up)
   `redis_ping_seconds`. `classifySaturation` is unit-tested for `ok/warn/critical` across each signal,
   and an alert rule per signal exists in `alerts.yml`.
4. **Statelessness proven** — an integration test signs up on app instance A and successfully
   authenticates the returned `rid` on a *separate* app instance B over the same Postgres/Redis,
   proving there is no in-memory session affinity (any replica can serve any request).
5. **Capacity numbers in docs produced by the suite** — `docs/capacity.md` is written by the perf run
   with the measured req/s, p50/p99, and **req/s per vCPU** per scenario; `docs/scaling.md` documents
   statelessness, the worker-concurrency knobs, and the horizontal scale-out model derived from those
   numbers (no guessed figures).
6. **Cost forecast pure module unit-tested** — `forecastUsage` yields zeros for an empty trend, a flat
   projection for one point, and a linear projection for a rising/falling trend; `recommendRightSizing`
   returns scale-up (high utilization or projected-over-budget), scale-down (idle), hold (otherwise);
   `infraBudgetStatus` flags a breach only against a positive ceiling. All branches unit-tested.
7. **Forecast surfaced in the Founder Console** — the #104 roll-up gains a `costForecast` view
   (projection + right-sizing + infra-budget status), wired through the existing read seams over
   `tenant_usage` + the resolved `scale` caps, integration-tested end-to-end on real Postgres.
8. **No weakened existing tests / no new authority** — the suite injects fakes for heavy paths (no
   agent-process spawn), the saturation sampler reuses existing `getPool`/`getRedis`, and every config
   addition is optional with a no-op default. Nothing here mutates tenant data.

## Seams (pure decision + IO orchestrator)

```
src/perf/budgets.ts        pure: PerfResult/PerfBudget types, summarize(samplesMs), percentile, evaluateBudgets, rpsPerVcpu
src/perf/driver.ts         runLoad(opts, request, clock?) → PerfResult   (closed-loop worker pool; injectable clock)
src/perf/scenarios.ts      HOT_PATH_BUDGETS + buildScenarios(baseUrl, fetch) — the hot-path request fns + their budgets
scripts/perf.ts            CLI: boot app (fakes for heavy deps), listen, run scenarios, write docs/capacity.md, exit on breach
src/observability/saturation.ts  pure classifySaturation + SaturationSample/Thresholds + collectSaturation(deps) + eventLoopLagSeconds()
src/observability/metrics.ts     +setSaturationSample / render gauges (queue_depth, event_loop_lag_seconds, pg_pool_connections, redis_ping_seconds)
src/observability/plugin.ts      registerObservability(app, { saturation? }) — sample at scrape, fail-soft, then render
src/scale/forecast.ts      pure forecastUsage / recommendRightSizing / infraBudgetStatus + UsageTrendPoint/CostForecast types
src/scale/caps.ts          +infraBudgetCeilingCents resolved on ScaleCaps (default 0)
src/founder-console/aggregate.ts  +costForecast view computed via scale/forecast from the gathered trend + caps
src/db/repositories/tenant-usage.ts  +getUsageTrend(workspaceId, windowKeys[]) — read the last N windows (additive read)
```

IO wiring (all injected; tests pass fakes):

- **Saturation deps** (`plugin.ts` ← `app.ts`): `pgPoolStats()` from `getPool().{totalCount,idleCount,waitingCount}`,
  `redisPing()` a timed `getRedis().ping()` (null when absent), `eventLoopLagSeconds()` from a
  process-singleton `monitorEventLoopDelay`, `queueDepth()` from `scale.admission.snapshot("").global`.
- **Forecast deps** (`founder-console/default.ts`): the existing `getUsageTrend` over `tenant_usage` +
  `resolveScaleCaps(scale.config(ws).scale)` for the budget cap, tenant concurrency, and the new infra
  ceiling; live `scale.admission.snapshot(ws).tenant` for utilization.
- **Perf scenarios** (`scripts/perf.ts`): `buildApp({ sessionManager: fake })` + `app.listen({port:0})`,
  a signed-up `rid` cookie, and the global `fetch` as the HTTP client — no autocannon/k6 binary.

## Why a dependency-free load driver (not autocannon/k6)

Consistent with #19 (a dependency-free Prometheus subset rather than `prom-client`) and #11 (a
hand-rolled OpenAPI doc rather than a Swagger dep), the load driver is a small, correct closed-loop
TypeScript harness over the global `fetch` — no new runtime/dev dependency, no separate binary to
install in CI, and the budget/percentile math is unit-testable without a network. The named tools
(autocannon/k6) would add a dependency and a non-deterministic, install-gated CI step for no gain over
a ~100-line driver we can test directly. See ADR-0113.

## Out of scope (deferred behind seams, like #105)

- **Distributed/multi-box load generation.** The driver is single-process closed-loop; a coordinated
  multi-worker generator (or adopting k6 for very high RPS) plugs in behind the same `runLoad`/`PerfResult`
  contract and `evaluateBudgets` gate.
- **Auto-scaling actuation.** Right-sizing is a *recommendation* surfaced to the founder; wiring it to
  actually change `scale.globalConcurrency`/replica count is a follow-up over the same `recommendRightSizing`
  output.
- **Wiring saturation into the watchdog decision.** `classifySaturation` is exposed as the seam and the
  alerts fire on it; feeding it into `decideRevival` (e.g. pause revivals when the box is critical) reuses
  the existing watchdog dep wiring and is deferred to keep this slice additive.
- **Hammering write/spend hot paths (session launch, venture advance) in CI.** The suite measures their
  HTTP/auth/admission overhead via injected fakes; driving the real agent runtime / real spend at load
  is a soak concern (the existing `soak` script), not the per-PR budget gate.
