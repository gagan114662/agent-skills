# ADR-0268: Email deliverability + compliance pipeline for Postmark — gated, dry-run by default

- **Status:** Accepted
- **Date:** 2026-06-18
- **Context issue:** [#268](https://github.com/gagan114662/agent-skills/issues/268)
- **Builds on:** [ADR-0189](0189-acquisition-execution.md) (suppression list, CAN-SPAM/GDPR footer, domain warmup, the signature-verified ESP bounce/complaint webhook), [ADR-0264](0264-dns-automation-cloudflare.md) (the `DnsManager` that publishes + verifies SPF/DKIM/DMARC with zero hand edits), [ADR-0243](0243-money-only-approval.md) (a real send is not money but is the irreversible class), [ADR-0225](0225-outreach-engine.md) (the `outreach.send` structural always-gate this mirrors), [ADR-0200](0200-premortem-panel.md) (the standing premortem this answers), [ADR-0192](0192-external-account-onboarding.md) (the write-only credential vault), [ADR-0267](0267-central-provisioning.md) (the provider-response quarantine pattern).

## Context
Email is the heaviest acquisition lane and the most irreversible: a sent message is in a stranger's inbox forever and a cold blast torches sender reputation permanently (premortem #200 §4). #189 already shipped most of the *compliance* primitives (suppression, footer, warmup, bounce/complaint webhook → suppression), and #264 already publishes + verifies SPF/DKIM/DMARC with no manual DNS work. What #268 adds is the **deliverability + live-send pipeline for Postmark** that sits on top of those seams and answers the premortem's hardest rules — *never assume success* (#200 §3), *irreversible → pre-commit + human gate* (#200 §4), *injection defense on any web-sourced content* (#200 §6) — while keeping real sending **OFF by default**.

The non-negotiable constraint: this PR must not send a real email or connect a live sending account. So every new live capability is gated behind a default-OFF flag, an owner-first rollout, a connected Postmark token, AND a per-send owner approval — and the byte-for-byte default everywhere stays the recorded-only dry-run sender.

## Decisions
1. **A gated live Postmark provider behind the existing `EspSender` seam.** `email/postmark-provider.ts`'s `PostmarkEspProvider` implements the same `EspSender` contract as the recorded-only `dryRunEspSender` (#280) — dependency-free (Postmark v1 REST over global `fetch`, no SDK), with `fetch` injectable for offline tests. It is constructed ONLY by `resolvePostmarkSender`, which returns the **dry-run sender** unless live sending is explicitly enabled AND a server token + From address are connected. So CI, tests, and any default deployment never touch the network. The server token is a secret — it rides only the `X-Postmark-Server-Token` header, never the request body, never a log line, never a thrown error. The Postmark `MessageID` is captured as the **external receipt** (#200 §2/§3). *This PR does not wire `resolvePostmarkSender` into the autonomous reach channel — that wiring is the owner's gated follow-up.*
2. **Deliverability is verified against reality, never assumed (#200 §3).** `email/deliverability.ts` grades two tiers: `assessSenderAuth` reads the published SPF/DKIM/DMARC config (the #264 verify receipts) where a missing record is `unknown`, never `pass`; `parseAuthenticationResults` reads the `Authentication-Results` header of a **delivered** message. `confirmDeliverability` combines them — a sender is deliverable ONLY when the config is aligned AND a real delivered-message header confirms all three pass. Config alignment alone is explicitly insufficient: without a production header receipt the verdict is `false` with a reason. That is the premortem's "verification must touch reality" rule made structural.
3. **One-click unsubscribe is RFC 8058 and unforgeable.** `email/one-click-unsubscribe.ts` builds the `List-Unsubscribe` + `List-Unsubscribe-Post: List-Unsubscribe=One-Click` headers and an HMAC token bound to the normalized recipient (no PII in the token). A new **unauthenticated but token-verified** route `POST /email/unsubscribe/:wid` honors a mailbox provider's one-click POST: only a link we actually issued (a token that verifies for that recipient) adds an `unsubscribe` suppression to the reused #189 list. The unsubscribe secret lives in the #192 vault, never config.
4. **Rate caps bound the burst, orthogonal to warmup.** `email/rate-cap.ts`'s `rateCapAllows` is a rolling-window (per-minute/hour) cap; `combineSendCaps` takes the most-restrictive of the existing per-day warmup (#189) and the rolling cap, so a burst can't blow past the provider limit even mid-warmup. Pure, `now` injected.
5. **A real send is the structural `email.live_send` #13 always-gate (#200 §4).** `email/live-send.ts`'s `decidePostmarkLiveSend` is the single seam that says whether a real send may execute. It composes every safeguard — the flag (`isLiveSendEnabledForWorkspace`, default OFF + owner-first), the #189 compliance gate, the §3 deliverability confirmation, the warmup+rate budget, and the §6 quarantine assertion — and then REQUIRES an owner `approvalRequestId` on top. There is **no input that makes `proceed` true without an approval id**; that invariant is the pre-commitment the premortem demands. The new `EMAIL_LIVE_SEND_ACTION` is added to `approvals/policy.ts` alongside `outreach.send`: it is NOT a money action (so it is not in `MONEY_ACTIONS`); the always-gate is enforced *structurally by this decision*, exactly like `outreach.send`/`hosted.publish`.
6. **Injection defense is a precondition of the gate (#200 §6).** Any externally-sourced content (a prospect's company facts, a web-read snippet) must pass through the existing quarantine/sanitization (`sanitizeProviderText`, ADR-0267/#223) before it can compose a send; `decidePostmarkLiveSend` blocks unless `contentQuarantined` is asserted. A poisoned read can never steer an autonomous send.

## Consequences
- **Default-OFF and migration-free.** The whole live capability rides the new `emailDeliverability` config block (`liveSendEnabled` default OFF, `ownerWorkspaceOnly` default true, env `RELOAD_EMAIL_LIVE_SEND_ENABLED` / `RELOAD_EMAIL_OWNER_WORKSPACE_ID`). Suppression already has a table (#189), and the gate is config-resolved + parked against the existing `approval_policies` — so **no migration is needed**. The dry-run sender remains the byte-for-byte default.
- The pieces are pure and composable: `confirmDeliverability`, `decidePostmarkLiveSend`, `combineSendCaps`, and the unsubscribe/header builders are all total functions, unit-tested offline with `fetch` injected for the one provider that does IO.
- The live executor (calling `resolvePostmarkSender(...).send(...)` after an approval) and a deliverability status route are deliberately a **future, owner-approved step** — this PR leaves that wiring gated, as the issue requires.

## Verification
Unit suites prove, with no network: deliverability is `unknown` for missing records and `false` without a delivered-message header even when config is aligned (#200 §3); the one-click token round-trips, is recipient-bound, fails closed without a secret, and the RFC 8058 headers are exact; the rolling-window cap counts only in-window sends and `combineSendCaps` takes the binding cap; `decidePostmarkLiveSend` is never autonomous and never `proceed`s without an approval id, the flag is OFF by default + owner-first, and each safeguard (compliance, deliverability, budget, quarantine) independently blocks; `resolvePostmarkSender` returns dry-run unless live+token, and `PostmarkEspProvider` POSTs the right shape, carries the token only in the header, forwards List-Unsubscribe headers, throws on `ErrorCode != 0` / non-2xx, and never leaks the token in an error. Gates: tsc, eslint, the full server unit suite, build, and the skill-colocation check are green.
