# ADR-0012: ACP + A2A Protocol Adapters

- **Status:** Accepted (Gagan launched the #12 lifecycle with "implement it fully")
- **Date:** 2026-06-08
- **Context issue:** [#12](https://github.com/gagan114662/agent-skills/issues/12) (Phase 2 — Agent integration)
- **Builds on:** [ADR-0003](0003-auth-identity.md), [ADR-0004](0004-channels-dms.md),
  [ADR-0006](0006-threads-mentions.md), [ADR-0009](0009-registry-rbac.md),
  [ADR-0011](0011-rest-cli.md), [ADR-0014](0014-tasks.md), [ADR-0025](0025-cloud-execution.md)

## Context
Reload's reach is "any agent framework can join" (#11). #11 delivered that for agents willing to
call Reload's own REST contract. But a growing set of frameworks (Google ADK, LangGraph, BeeAI,
CrewAI bridges) speak two **published** agent standards natively — **A2A** (Agent2Agent: AgentCard
discovery + JSON-RPC) and **ACP** (Agent Communication Protocol: REST runs over messages). Such an
agent otherwise needs a hand-written shim per integration. #12 makes Reload *speak the protocols* so
those agents talk to it — and hand work to each other through it — with no custom glue. The risk in
"add two protocol surfaces" is re-implementing a second, divergent auth/tenancy/RBAC. We explicitly
reject that, exactly as #11 did.

## Decisions

1. **The adapters compose the existing model — no new table, no new authority.** An A2A handoff
   becomes a #14 **task** assigned to the receiving agent; an ACP run becomes a #6 **thread** in a
   #4 channel. Both reuse the same helpers the native routes trust (`requireIdentity`,
   `requireChannelCapability`, `requireTaskInWorkspace`, `postMessage`, `createTask`, `updateStatus`,
   `resolveAndPersistMentions`), so listing/enforcement can never diverge and the protocol surface
   can never become a weaker side door. The only new persistence-layer code is **read-only**
   composition (`getAgentById`, `getAgentMemberByHandle`, `listMentionsOnMessage`). This mirrors
   #11's "reuse the routes, add the minimum" decision.

2. **An ACP run is realized as a channel thread.** ACP is run-centric; the acceptance criterion is
   "ACP messages map correctly to channels/threads." The most faithful, zero-new-table mapping makes
   the run **be** a thread: `run_id` = `session_id` = the thread-root message id; a new run's first
   input is the root (@mentioning the target agent so it is actionable, #6) and the rest are replies;
   a `session_id` continues that thread; the run's `output` is the target agent's in-thread replies;
   the run's `agent_name` is the first agent-kind member @mentioned on the root. Status is derived
   (`created` → no agent reply yet; `completed` → the agent has replied; `cancelled` → explicit
   cancel). We deliberately do **not** synchronously execute the agent here — live execution is
   #10/#25's runtime; an ACP client posts a run and polls. (A session-backed run, ACP run ⇄
   `agent_sessions`, is a noted follow-up.)

3. **An A2A handoff is realized as a task with its context preserved.** `message/send` to
   `:agentId` creates a task assigned to that agent, the message content flattened into the task's
   `description` (an `a2a` label marks it). `tasks/get` reconstructs the original message as the
   A2A `Task.history`, so the receiving agent gets the task **and the content intact** — the literal
   acceptance criterion. `tasks/cancel` maps to a guarded `canceled` transition. We chose JSON-RPC
   2.0 (A2A's default transport) and an HTTP-200-with-error-envelope convention; gRPC/HTTP+JSON
   transports and streaming/push are out of scope (the AgentCard advertises `streaming:false`,
   `pushNotifications:false`, so the capability statement is honest).

4. **The capability handshake (AgentCard / ACP manifest) is *derived*, not stored.** A registered
   agent (#3: `name`, `framework`) plus this server's URL plus the #9 auth posture is enough to emit
   a standards-compliant A2A `AgentCard` (with `bearerAuth` + a `handoff` skill; `framework` becomes
   a routing tag) and an ACP agent manifest. No new "card" table, no drift: the descriptor is a pure
   function of the registry, computed on read. Discovery is **workspace-scoped** — a card/manifest
   for another workspace's agent is a 404 (#3 IDOR).

5. **Conformance via vendored published-schema *subsets* + a dependency-free validator.** The
   acceptance criterion is "conformance tests pass." We validate every emitted object
   (`AgentCard`, A2A `Task`/`Message`, ACP `Agent`/`Run`/`Message`) against the published A2A/ACP
   JSON Schemas, vendored as **focused subsets** (the exact `$defs` we emit) under
   `apps/server/test/fixtures/{a2a,acp}.schema.json`, each pinned to a spec version with an
   `x-source` provenance pointer. We hand-roll a tiny JSON-Schema validator
   (`src/protocols/jsonschema.ts`) rather than add `ajv` — the **same** call #11 made when it
   hand-wrote its OpenAPI types instead of pulling in `@fastify/swagger`: no new dependency, no
   install/network in the build gates, and a small surface that is itself unit-tested. Negative
   tests prove the validator rejects malformed objects, so conformance is real, not vacuous.

6. **No migration.** #12 is pure interface + composition over existing data; it adds no table and no
   column, so the CI "prove down/up clean" step is untouched.

## Consequences
- An A2A or ACP agent — in any language/framework — interoperates with Reload using nothing but its
  native wire format + a Bearer token, reading the AgentCard/manifest first. Agents can hand tasks
  to each other through Reload with no shim.
- There is exactly one access-control implementation: the adapters inherit #3 tenancy and #9 RBAC
  unchanged. The cross-workspace-rejection integration tests guard this for both protocols.
- The published protocol surface stays small and curated, so it is cheap to keep documented and
  versioned; broadening it (A2A streaming/push, ACP live runs, gRPC) is additive.
- Deriving the AgentCard on read is O(1) per call and never drifts from the registry; the trade-off
  is that skills are coarse (`handoff`/`messaging` + framework tag) until a richer capability model
  exists.
- The conformance subset is *our* contract, not the full upstream file. If upstream tightens a
  schema we already emit, our pinned subset must be re-synced — a deliberate, low-frequency cost,
  documented by the `x-spec-version`/`x-source` headers.

## Alternatives considered
- **A dedicated `runs` / `a2a_tasks` table (or backing runs with #25 sessions).** Rejected as
  premature: a thread already *is* a run's conversation and a task already *is* a handoff; new
  tables would duplicate state and risk divergence. Noted as a follow-up if/when live execution or
  rich run status is needed.
- **`ajv` + the full upstream schema files.** Rejected: a new dependency + install during the build
  gates, and the full files pull hundreds of `$defs` (and draft-2020-12 features) we don't emit. The
  focused-subset + tiny-validator approach validates exactly what we ship, offline.
- **A2A streaming / push now.** Rejected: significant surface (SSE, subscription lifecycle) for no
  current consumer; the card honestly advertises it as unsupported and it is purely additive later.
- **An A2A/ACP client SDK.** Rejected as the antithesis of "no custom glue" — the point is that
  agents use the protocols they already speak.

## Follow-ups (deferred)
- Session-backed ACP runs (ACP run ⇄ #25 `agent_sessions`) so a run can *execute* and stream output,
  with full ACP status (`in-progress`/`awaiting`/`failed`).
- A2A `message/stream` (SSE) + `tasks/pushNotificationConfig/*` + `tasks/resubscribe`.
- Channel-linked A2A handoffs (post the handoff into a shared channel + `task_link`) when the sender
  supplies a channel both agents can access.
- gRPC / HTTP+JSON A2A transports.
- Binary `FilePart`/`DataPart` fidelity (artifact storage) beyond today's text normalization.
- Re-sync the vendored schema subsets when upstream A2A/ACP spec versions bump.
