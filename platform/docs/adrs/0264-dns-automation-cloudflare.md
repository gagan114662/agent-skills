# ADR-0264: Automate DNS end to end — a Cloudflare connector + a DnsManager the three blocked lanes call

- **Status:** Accepted
- **Date:** 2026-06-16
- **Context issue:** [#264](https://github.com/gagan114662/agent-skills/issues/264)
- **Builds on:** [ADR-0192](0192-external-account-onboarding.md) (the `DnsProvider` seam, the `dns_receipts` table, the write-only `external_credentials` vault), [ADR-0243](0243-money-only-approval.md) (registrar connect is autonomous, not a money action), [ADR-0223](0223-decision-maker-resolver.md) (injection-quarantine), [ADR-0231](0231-real-world-tool-surface.md) / [ADR-0250](0250-realworld-publish-site.md) (dependency-free REST providers over global `fetch`).

## Context
DNS is the single most pervasive non-technical blocker. A non-technical ipop user cannot edit DNS records, yet DNS gates **three lanes at once**: Google Search Console domain verification (a TXT record), email sender authentication (SPF/DKIM/DMARC), and attaching a custom domain to hosted pages (a CNAME, plus a CAA for the TLS cert). #192 already shipped the *shape* of DNS automation — a `DnsProvider` seam, pure record builders, an immutable receipt table — but only the no-network `DryRunDnsProvider` existed. Nothing actually wrote a record at a registrar. #264 lands the first **live** connector and a service the three lanes call so a domain is configured with **zero records edited by hand**.

## Decisions
1. **A live Cloudflare connector behind the existing `DnsProvider` seam.** `CloudflareDnsProvider` (`onboarding/dns/cloudflare-provider.ts`) implements the same `configure`/`verify` contract as the dry-run default — dependency-free (the Cloudflare v4 REST API over global `fetch`, no SDK), lazy (only constructed when a token resolves). `configure` resolves the zone (walking sub-domain labels up to the registrable apex), then for each planned record GETs to decide create-vs-update and POSTs/PUTs accordingly; CAA records are sent as Cloudflare structured `data`, everything else as `content`. `verify` re-reads each record and compares (normalizing TXT quoting / CNAME trailing dots). It **never throws**: a missing token, an unresolvable zone, or an API error degrades to `failed` receipts.
2. **The seam is the connector layer.** GoDaddy / Namecheap / Route53 each slot in as a sibling class implementing `DnsProvider`, registered as a new `case` in `createDnsProvider` — no change to the manager or the lanes. Selection is the existing non-secret `onboarding.dnsProvider` config; a selected-but-unconnected provider falls through to dry-run rather than throwing.
3. **The connection is a per-workspace, encrypted, write-only credential — and it is autonomous, not a money action.** The Cloudflare API token is pasted ONCE through the existing #192 connect route (service key `cloudflare`, kind `registrar`), sealed in the `external_credentials` vault, and resolved per-workspace at configure time (env `CLOUDFLARE_API_TOKEN` is honored as a server-wide fallback, mirroring `REALWORLD_GITHUB_TOKEN`). It is **never echoed** to the user and **never logged** — it rides only the `Authorization` header. Per #243, connecting/using a registrar is reversible and money-free, so it is autonomous (a physical paste-the-key step on the checklist, not an owner approval).
4. **`DnsManager` is the one service the three lanes call.** `onboarding/dns/manager.ts` exposes `verifyDomain()` (Search Console / reload ownership TXT), `ensureEmailAuth()` (SPF/DKIM/DMARC), `ensureSiteCname()` (CNAME + CAA), and `setupDomain()` (every lane the inputs cover, in one pass — the "connect a domain" flow). Each call resolves the workspace's provider, configures, records an immutable receipt per record, re-reads to **verify**, records those too, and returns the verified outcome + a roll-up. New routes `POST /me/dns/{verify-domain,email-auth,site-cname,setup}` expose the lanes (gated behind `onboarding.enabled`).
5. **Money-gating + injection-quarantine stay intact — structurally.** The manager has NO approvals/send/spend seam (writing DNS is reversible and money-free). The connector returns DATA-only `DnsReceiptResult`s; registrar API strings (ids, errors) are truncated into the receipt `detail` for human display and never parsed back into an autonomous action or a prompt (injection-quarantine, #223). No new money action, no new approval path.

## Consequences
- **Default-OFF and migration-free.** The whole feature rides `onboarding.enabled` (writes 409 otherwise) and `onboarding.dnsProvider: "cloudflare"`. The receipt `purpose`/`status`/`provider` values are all already covered by the #192 schema (`provider` is free text), so **no migration is needed**.
- The dry-run provider stays the default everywhere, so CI/tests/the demo need no Cloudflare token and touch no network. `createDnsProvider({provider:"cloudflare"})` with no token still returns dry-run.
- Google Search Console gets a real `google-site-verification` TXT builder; there is still no GSC *API* connector (the user copies the token from the Search Console UI — a one-time copy, not a DNS edit).

## Verification
Unit suites prove, with the registrar API mocked via `vi.stubGlobal("fetch", …)` (no network): the connector resolves the zone and CREATEs new records / UPDATEs existing ones / sends CAA as structured `data` / walks sub-domains to the apex / carries the token only in the Authorization header (never a log line) / verifies matching content and fails on mismatch-or-missing / degrades every failure mode to `failed` receipts without throwing. The `DnsManager` tests prove each lane plans the correct records and writes both configure and verify receipt batches, with no money/approval seam on the manager. Gates: tsc, eslint, full server unit suite green.
